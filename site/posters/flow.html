How a lab is reached

From a browser anywhere to the lab's interfaces inside its VM, and what decides who gets through. Everything of remote access runs on the lab host, next to the lab: nothing is added to the lab's VM. Drawn as running for rdk-emosa on rev120.

From the browser to the lab, end to end

1 · reach: the browser over Tailscale to the lab's device and its gateway 2 · reserve: the room asked first whether someone holds it locally 3 · use: the gateway forwards the one reserved browser to the lab 4 · the lab network: open while private, closed for a public lab

1Reach

Nothing on any router is opened. The lab's address only exists on the tailnet.

  1. The browser opens https://rdk-emosa.<tailnet>.ts.net/_remote/. Tailscale carries it, peer to peer or through a relay, with a certificate for the lab's own name.
  2. It arrives at the lab's device: a tailscaled of the lab's own on rev120, beside the host's. Serve answers on 443, 8443 and 10000 only; any other port of the lab's name is refused.
  3. Serve hands each port to the gateway on the lab's loopback address, 127.77.136.185:40285–40287. The device may reach nothing else on the host's loopback (its systemd unit says so).
  4. The gateway checks the host name and, for every write, the origin: nothing from another site gets in.

2Sign in and reserve

One person drives the lab; everyone signed in can see who.

  1. Sign-in: the account's password checked against its scrypt hash (rdk-emosa.users.json); a random session token in a __Host- cookie, kept 8 hours. Five tries a minute per name.
  2. Reserve: the gateway asks the room (/api/demo/interactions) whether someone holds it locally; if so, it refuses.
  3. One slot in SQLite takes the reservation: this browser's session, an idle deadline (10 minutes) and a hard one (60).
  4. It ends by release, sign-out, idle, the limit, an admin or maintenance; open streams close within a second, and the next reservation waits 125 s.

3Use

Each interface keeps its own address; the page frames them, the gateway carries them.

  1. Every request of the reserved browser is forwarded: plain HTTP, the room's event stream, the controller's and Console NG's WebSockets. Anyone else gets 423.
  2. The gateway removes its own cookie and any identity headers before the lab, and lets only the lab's own origins frame what it returns.
  3. It reaches the lab through the host's LXD proxy devices, 192.168.2.120:20110–20112, which NAT into the VM's :8888, :8890, :8891.
  4. In the page each interface sits in a tile on its own origin; the tile sees real input there and renews the reservation.

4The lab network

Trusted (requirement Q3): what the lab offered on it before still works.

  1. On the LAN the lab's ports answer as before: bookmarks, and rev150's room suites against this lab.
  2. Someone there can drive the lab while a remote person holds it: run local work under maintenance until local tools take the reservation (step 6).
  3. A lab published publicly, or with --close-lan, gets the firewall: a table of its own drops traffic from the network to its ports and to the VM's addresses, before LXD's NAT.
  4. The host's own connections always pass: the gateway's, and an operator's SSH tunnel.
